# Security and privacy

Report vulnerabilities privately through the repository's GitHub **Security → Report a vulnerability** feature once the repository is published and private vulnerability reporting is enabled. Do not post secrets or exploit payloads in public issues. Until a private reporting channel exists, contact the repository owner through an established private channel.

## Trust boundaries

- Model-generated JavaScript runs in QuickJS compiled to WebAssembly, inside a fresh Node worker thread. It is not evaluated by Node `eval`, `Function` or `vm`. Worker threads are not themselves a security boundary; isolation depends on QuickJS/WASM and the narrow JSON bridge.
- Search receives the local API specification and no request bridge. Execute receives only the generic `tamperbox.request` bridge to documented methods/paths. The guest has no Node objects, credentials, environment variables, filesystem, arbitrary URL fetching or module loader. The host validates every allowlisted operation and its arguments again before a REST call.
- The parent enforces wall time, aggregate call count, parallelism and output limits. The guest has a 32 MiB QuickJS allocator budget, 512 KiB stack limit, interrupt limits and a separate hard 64 MiB WebAssembly linear-memory ceiling. The allocator budget alone does not constrain every backing store; the hard ceiling also covers ArrayBuffer and typed-array storage. Neither number bounds total host RSS. Timed-out workers are terminated; pending fetches are aborted. No background guest execution is retained.
- Each API request uses a fixed path from the catalog, a trusted operator-configured origin and `redirect: error`. Guests cannot choose an arbitrary API URL or headers. The request path must match the bundled specification, including validated path/query/body fields. A documented diagnostic body can name a public target for the upstream service to check; the upstream API owns DNS/redirect/private-target restrictions and probe limits. Configuration is trusted: changing the origin changes who receives data. The bridge does not follow references inside API documents.
- API errors are sanitized: raw upstream error bodies, host exception messages and private configuration URLs are not copied into responses. Guest-originated error names, bounded messages and source line numbers are returned to the caller for debugging; they may include guest-supplied data. Validation diagnostics expose schema paths and rules, not argument values. Diagnostic extraction avoids ordinary getters and stays inside the interruptible VM; hostile proxy traps remain subject to the execution deadline. None of these diagnostics or inputs are logged. Returned successful tool data is visible to the caller and may contain user-provided content; treat it as untrusted data, not instructions.
- HTTP checks Host and Origin, bounds request sizes and time, rejects JSON-RPC batches and applies process-wide request/execution limits. Forwarding headers do not confer trust. CORS is not authentication.
- The optional inbound bearer token is a static operator secret compared using constant-time hash comparison. It is not forwarded upstream or exposed inside the sandbox. This is **not an OAuth authorization server**. Clients requiring OAuth need a conforming gateway. Anonymous HTTPS deployments support clients that accept no authentication.

## Hosting responsibilities

Keep Node and dependencies patched. Run under a non-root account with a read-only filesystem and container/process memory and CPU limits. Place internet-facing deployments behind HTTPS, connection/body limits and distributed abuse protection. In-process quotas are not global quotas across replicas. Do not expose an unrestricted publicly writable deployment or put unrelated secrets in the service environment.

The server makes no persistence or diagnostic logs of tool input/output. Reverse proxies, API hosts, AI clients and model providers have separate retention policies. Do not claim end-to-end zero retention. MCP `search` reads only bundled public metadata and makes no network call. The separate upstream directory endpoint sends query text in a URL; use task keywords only. Remote diagnostic inputs, including header text, go to the configured API. Caller-IP, connection and own-port results describe the request reaching that API, which can be the MCP server or shared gateway rather than the human device.

Supported release line: 0.1.x. Dependencies are pinned and audited in CI. There is no claim of independent penetration testing or formal sandbox verification.
